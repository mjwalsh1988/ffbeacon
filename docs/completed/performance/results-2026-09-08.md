# Site speed build: what actually changed, measured

Written 2026-09-08, immediately after the build described in
`site-speed-audit-and-plan.md` Part 8. The baseline this is measured against is
`db-baseline-2026-09-08.md`, recorded the same day just before Phase 1, and
`pg_stat_statements` was reset at the end of that recording.

Read this next to Part 9 of the plan, which sets the targets. Two of the four
measurement sources in that protocol are NOT available yet and this file says so
rather than guessing:

- FIELD DATA. `@vercel/speed-insights` was added by PERF-T001 but it has to be
  deployed and then collect seven days before it can report a p75. There are no
  real-user Web Vitals in this file.
- THE VERCEL FUNCTION LOG. Nothing here is deployed, so per-route server
  durations cannot be compared. The query plans below are the server-side
  evidence available today.

## Query plans, measured on production after the change

Every number below is from `EXPLAIN (ANALYZE, BUFFERS)` run against the
production database. The before numbers are the audit's, from the same method.

| What | Before | After | Where |
| --- | --- | --- | --- |
| Sleeper-id player lookup, fallback pass | Seq Scan, 10,473 rows removed, 1,319.8 ms | Bitmap Index Scan on idx_players_sleeper_slug_tail, 0.12 ms warm at 5 ids; at the code's real chunk of 100 the planner picks a Seq Scan instead, 8.2 ms | 4.1, PERF-T010 |
| Sleeper-id player lookup, indexed pass | part of the same defeated OR | BitmapOr on idx_players_external_sleeper, 0.82 ms warm at 50 ids | 4.1, PERF-T010 |
| Signal Scout positional finishes | `get_player_positional_finishes` RPC, 686 ms mean over 7,857 calls | Index Scan on the primary key, 0.108 ms | 4.5, PERF-T011 |
| Draft market latest per player | Seq Scan then an external merge sort spilling 16 MB, 1,330 ms | Index scan on the new table, 0.479 ms | 4.6, PERF-T012 |
| Latest value row for one source | No index leading with `source`, 537 ms mean, 7.5 s max | Index Only Scan, 0 heap fetches, 1.53 ms | 4.8, PERF-T013 |
| Player name search | OR across three columns, two of them unindexed, so a sequential scan | Bitmap Index Scan on idx_players_search_name_trgm, 1.9 ms | 4.9, PERF-T050 |

The one to keep an eye on is the first. `players` had logged 81,321 sequential
scans on a 10,481 row table, and that counter is what should stop climbing.

## Round trips removed from a page render

Counted from the code, not measured, because nothing is deployed. At the
gateway's measured 45 to 50 ms per read, each of these is roughly that much
wall time off the critical path.

| Page | Before | After |
| --- | --- | --- |
| League overview, warm cache | 9 to 11 reads in series | 3 waves: the league row, then a parallel wave, then the format row |
| Every page's header | 4 reads in front of the page's own data | 3 of the 4 are now in-process memo hits, and the whole group is behind a Suspense boundary |
| Site search, per settled keystroke | 2 reads in series, one unindexed | 1 read, indexed |
| Rankings board | 3 reads including an unbounded history read | 3 reads, the unbounded one replaced by a single row |
| Signed-in navigation | 2 auth round trips | 1, once the ES256 key is the current signing key (see below) |
| League sync worker, idle tick | about 12 requests | 5: acquire, the reap select, the finalize select, the tick RPC, the release. No ledger row. Part 9 asks for 3; see PERF-R008 |

### A correction the review made to this table

The first row originally claimed a Bitmap Index Scan for the player lookup
without naming the chunk size it was measured at. At the code's real chunk of
100 ids the planner misjudges selectivity on that column and picks a sequential
scan instead. It is still about 160 times faster than what it replaced, and the
fallback pass runs almost never because the indexed pass resolves every id on
the current corpus, but the plan is not the one the first draft of this file
claimed. Recorded rather than quietly corrected, because the difference between
a measurement and an example is the whole value of this document.

## Database housekeeping

- `player_value_history`: 29,251 dead tuples and last autovacuumed 2026-08-11,
  now 0 and vacuumed today. Autovacuum scale factors tightened from the default
  0.2 to 0.02, so a 2M row table is vacuumed after about 40k dead rows rather
  than 400k.
- `player_stats`: 41,328 dead tuples and last autovacuumed 2026-07-24, now 0.
  Same thresholds.
- 58 RLS policies rewritten to the initplan form. The advisor's
  `auth_rls_initplan` finding went from 58 to 0, and
  `multiple_permissive_policies` stayed at 6, which is the design (own rows plus
  public rows) and was deliberately not touched.
- 13 unused indexes dropped. The advisor's `unused_index` finding went from 47
  to 34 and `unindexed_foreign_keys` stayed at 53, which is the proof that none
  of the thirteen was quietly backing a key.
- 7 foreign-key indexes added on the read paths named in 6.1.

## What is measured but not yet believable

The `getClaims()` change in middleware is correct either way, but it only
removes the 70 ms auth round trip if the project's published ES256 key is the
CURRENT signing key rather than a standby. The key is published (one key, kid
568e36a4, alg ES256, confirmed at the JWKS endpoint today), but current versus
standby cannot be read from outside. If it is standby, auth-js falls back to the
network call and this row of the table stays at 2 until somebody rotates it in
the Supabase dashboard under Authentication, JWT signing keys.

## How to re-run this

1. `docs/performance/db-baseline-2026-09-08.md` carries the three SQL queries.
   Run them again for the after-window totals; the ledger starts from
   2026-09-08.
2. `npm run build` then `npm run measure:bundle` writes
   `docs/performance/bundle-<date>.txt`.
3. Speed Insights p75 for the six routes in Part 9, after seven days of data.
