Please do any necessary source-code review and Sleeper API research needed to confirm the endpoint shape and expected fields.

Implement this using our existing Supabase table/migration patterns.

- Player projection data by player
- Sleeper ADP by player
- ADP for every format Sleeper provides from that endpoint
- Proper association to our existing players table wherever possible
- Clean timestamps / update tracking
- Idempotent nightly updates so repeated runs do not create duplicate rows
- Consistent table naming, column naming, indexes, and RLS/security patterns based on the existing project

The purpose of this data is to make Sleeper ADP available inside On The Clock and future FF Beacon features.

# 4. Add draft-level snapshot/cache for On The Clock

We need a performance-friendly way to cache/snapshot each draft so that once a draft is completed, the results do not change later.

Right now, if the awards, grades, board view, list view, or value calculations always pull current FF Beacon values and current Sleeper ADP, then finished draft results will change over time. That cannot happen.

Create a draft-level snapshot/cache system for On The Clock.

The snapshot should preserve the relevant data needed to accurately reload and grade a draft later, including:

- Draft ID
- League ID
- User/team/roster mappings
- Draft settings
- Draft type/format detected
- Draft status
- Draft rounds
- Draft picks
- Player IDs
- Player display names at time of snapshot
- Player positions/teams at time of snapshot
- FF Beacon value/rank used for that draft
- Sleeper ADP used for that draft
- ADP vs Beacon difference
- Pick-by-pick value result
- Award-relevant calculated data
- Any other fields needed to re-render completed draft results without recalculating from moving current data

This can be implemented as one or more tables depending on what is cleanest.

Possible table ideas:

- `on_the_clock_draft_snapshots`
- `on_the_clock_draft_pick_snapshots`
- `on_the_clock_award_snapshots`

Or a combined draft snapshot table with a structured JSONB payload if that is more appropriate.

Please choose a design that balances:

- Query performance
- Long-term maintainability
- Easy historical review
- Avoiding excessive recalculation
- Avoiding giant unstructured blobs where relational data would be better
- Still keeping a `meta` JSONB or snapshot payload when useful

# 5. Snapshot timing rules

Implement clear rules for when a draft snapshot is created or updated.

## Active or pre-draft drafts

For drafts that are still active, pre-draft, or in progress:

- It is okay for the tool to refresh draft state from Sleeper
- It is okay for values/ADP to update while the draft is ongoing
- Consider caching enough to avoid excessive API calls
- Avoid recalculating expensive data on every page load if a short-lived cache would be better

## Finished drafts that were already used in FF Beacon

Once a draft is completed:

- Create or finalize a permanent snapshot
- Lock the values/ADP/award calculations to that completed snapshot
- Future page loads should use the finalized snapshot
- Do not let current ADP or current FF Beacon values change the historical results
- If recalculation is needed later, it should be intentional/admin-driven, not automatic

## Finished drafts opened for the first time after completion

This is the important edge case.

If a user opens a completed Sleeper draft that was never previously used in FF Beacon, we still need to generate a historically reasonable snapshot.

In that case:

- Pull the completed draft data from Sleeper
- Determine when the draft happened or when it completed
- Use the best available historical FF Beacon values from that time period
- Use the best available historical Sleeper ADP/projection snapshot from that time period
- Generate and save a finalized draft snapshot based on those historical values
- Future loads should use that saved snapshot

If an exact historical date match is not available, use the nearest available snapshot before the draft completion date.

If no prior snapshot exists, use the nearest available snapshot after the draft completion date and clearly mark the snapshot as estimated/fallback in metadata.

The goal is to avoid using today’s values for an old completed draft unless there is truly no better option.

# 6. Historical lookup strategy

Please implement or design a clean helper/service layer for historical value lookup.

We need reusable logic that can do something like:

- Given a draft ID and draft completion date
- Determine the correct league format
- Determine the relevant player pool
- Find the closest FF Beacon value snapshot from that time
- Find the closest Sleeper ADP/projection snapshot from that time
- Return the correct value/ADP data to use for snapshot generation

This helper should be reusable for:

- Board view
- List view
- Awards
- Finished draft review
- Future historical tools

Suggested lookup priority:

1. Exact snapshot date matching the draft date/time
2. Closest snapshot before the draft completion date
3. Closest snapshot during the draft window
4. Closest snapshot after the draft completion date
5. Current data only as a last resort

When a fallback is used, store that information in metadata so we know how the snapshot was created.

Example metadata fields:

- `value_snapshot_source`: `exact`, `previous`, `during_draft`, `next_available`, or `current_fallback`
- `adp_snapshot_source`: `exact`, `previous`, `during_draft`, `next_available`, or `current_fallback`
- `value_snapshot_date`
- `adp_snapshot_date`
- `draft_completed_at`
- `snapshot_finalized_at`
- `snapshot_confidence`: `high`, `medium`, or `low`

# 15. Performance and API safety

Please be careful with performance.

Avoid repeatedly pulling the same completed draft from Sleeper and recalculating everything on every page load.

Use a cache/snapshot-first strategy:

- Check for existing finalized snapshot
- If it exists, use it
- If it does not exist and draft is completed, generate it once and save it
- If draft is active, use live mode with sensible short-lived caching if needed

Also be careful with the nightly cron job:

- Do not create unnecessary duplicate rows
- Do not make excessive Sleeper API calls
- Use batching where appropriate
- Log failures clearly
- Make partial failures recoverable
- Make reruns safe
